# CLAUDE.md

Guidance for any Claude Code session (or other AI assistant) working in this repository.

## What this project is

GeoWorld Framework is a **Python 3.10+ scientific research pipeline** — not a web application, not a library meant for `pip install`, not a set of ad-hoc scripts. It is doctoral research software (UFMG) that runs nine sequential geospatial-analysis phases per country (data audit → grid alignment → suitability criteria → MCDA suitability → energy potential → LCOE → results synthesis → GHG abatement → sensitivity analysis → transport decarbonization) and produces artifacts (GeoTIFFs, PNGs, CSVs, JSON reports) intended for peer-reviewed publication.

Treat it accordingly: prefer scientific correctness and reproducibility vocabulary over web-app vocabulary (there are "phases," not "routes"; "processors," not "controllers"; "artifacts," not "responses").

## Mandatory initial context rule

**Before any implementation, fix, refactoring, or investigation**, read [`docs/memory/README.md`](docs/memory/README.md) and follow its recommended reading order. Only investigate the code directly after consulting existing documentation.

- If documentation is outdated or contradicts the code, **the code is the final source of truth** — but you must correct the documentation before finishing the task.
- For any behavior you cannot confirm with certainty (undocumented intent, ambiguous naming, unclear precedence), flag it explicitly with:
  > ⚠️ Point to validate: \<what wasn't clear\>

## Mandatory documentation update rule

When finishing any task that changes architecture, behavior, algorithms, data structures, pipeline phases, dependencies, configuration, or any other relevant technical decision, **update the corresponding file(s) in `/docs/memory` and the index in `/docs/memory/README.md`**.

It is not mandatory to update documentation for a task with no structural impact (e.g., a narrow bug fix that doesn't change a documented flow or decision).

## Source of truth rule

Documentation in `/docs/memory` is memory and a guide for orientation. It never overrides what the actual code does. When in doubt, read the code.

## Project investigation and identification rule

Before applying any pattern from another kind of project, confirm this is still a Python geospatial research pipeline (check `main.py`, `configs/`, `src/core/pipeline_orchestrator.py`) rather than assuming it has become something else. Do not force web-application vocabulary or patterns onto it.

## Git rules

- Every modification requested must be committed when the user asks for a commit — never left uncommitted silently.
- **Never push without explicit authorization.** Never skip hooks (`--no-verify`).
- Always run `git log --oneline -20` before drafting a commit message and match the existing style. This repository's history is small and mixes styles (`feat: add main.py framework implementation` alongside plain imperative messages like `Update README.md`, `Fix Python version badge in README`, `Remove transport decarbonization phase details`). Default to a plain imperative summary line (`Fix X`, `Add Y`, `Update Z`) unless the user has established a stricter convention (e.g., Conventional Commits) in the meantime — **if genuinely ambiguous, ask the user which pattern to adopt rather than deciding unilaterally.**
- Commit messages must be objective and specific — never generic ("update", "fix stuff", "wip").
- No emojis (none appear in the existing history).
- **Never include** `Co-authored-by`, "Generated by Claude/AI," mentions of Claude/Anthropic, or any automatic AI signature/attribution in commits, code comments, or documentation, in any form.
- Never cite yourself as author, co-author, or tool used in commit messages, code, or docs.

## Code comment rules

Only add a comment when it explains a non-obvious rule, a dangerous behavior, or a real limitation (e.g., the reasoning behind `AlignedLayers` validating paths rather than open handles to avoid descriptor leaks; the polygon-vs-bounding-box masking rationale in `data_auditor.py`). Never write a comment that just restates what the code already says, and never a comment noting that something was written, suggested, or generated by AI.

## Implementation style rules

- Observe and reuse the patterns already in the codebase: Pydantic v2 contracts in `src/core/schemas.py`, the `PipelineOrchestrator` skip/cache contract, `GeoWorldStyler.render_raster_map()` for any new map, `src/utils/reporting.py` for any new text report, `timer()` from `src/utils/timing.py` for phase timing.
- Avoid introducing new libraries or architectural layers without a clear need — this is scientific code with a fixed dependency set documented in `requirements.txt` and `docs/memory/05-environment.md`.
- Avoid large unsolicited refactors. Prefer small, traceable changes.
- If you touch legacy or inconsistent code outside the task's scope, document it (in `docs/memory/06-risk-areas.md` or an ⚠️ note) instead of rewriting it.

## Bug investigation rules

Read `/docs/memory` first, identify the related module(s) via `SUMMARY.md`, reproduce the problem by tracing the actual code path (not by assumption), find the root cause, and avoid palliative/band-aid fixes — especially in numerically sensitive code (AHP/TOPSIS/OWA weighting, LCOE formulas, GHG abatement substitution logic).

## New features / experiments rules

Identify the closest existing pattern (e.g., a new sensitivity sub-analysis follows the SA-1…SA-6 structure in `sensitivity_analyzer.py`; a new criterion follows the pattern in `criteria_builder.py` and gets an entry in `settings.yaml`'s `visualization.criteria_meta`). Reuse structures rather than inventing parallel ones. Document new decisions and risks in `/docs/memory`.

## Scripts and commands rule

Document in `/docs/memory/10-scripts-and-commands.md` where each script lives, how to run it, what it's for, when to use it, and what environment variables/dependencies it needs. This is a local/manual-execution research pipeline (no CI, no notebook, no cluster scheduler currently in the repo) — say so explicitly rather than assuming one exists.

## Configuration rule

Document the reason and impact of any relevant configuration change in `/docs/memory/07-configuration.md`, particularly anything touching the `settings.yaml` vs. `parameters.json` precedence split (see `docs/memory/09-decisions.md`).

## Technical decisions format

Record decisions in `docs/memory/09-decisions.md` using: **Context**, **Decision**, **Consequences**, **Related files**, and **Status** (`Active` | `Legacy` | `In migration` | `Uncertain`). Mark explicitly as "inferred" any decision deduced from project structure rather than stated outright in code or commit history.

## Risk areas rule

Document large/generic code, duplication, missing tests, hardcoded values, fragile external dependencies (manual WDPA downloads, Terrascope credentials, Overpass API), and any other implicit or hard-to-reproduce behavior in `docs/memory/06-risk-areas.md`.

## Final rule

No generic work. Every implementation, documentation update, and commit must respect this project's actual nature (doctoral research pipeline, not a generic app), its existing patterns, and the persistent documentation in `/docs/memory`.
