## Phase 6 Overreach

Every metric `results_writer.py` recalculates instead of reading from an earlier phase's output, with exact lines and the phase that should own each one. This directly answers the three "critical focus" questions.

### §1 — Integrated suitable area (`km²`)

- **Recalculated at**: `results_writer.py::_compute_integrated_area`, **L434-481**, called unconditionally from `_format_report` at **L1434** for every tech/scenario in the report's summary table — it is never skipped even when a live `potential_results` dict with the real value is available.
- **Should be owned by**: **Phase 4** (`potential_calculator.py`).
- **Evidence Phase 4 already computes it**: `potential_calculator.py::_run_technology`, **L462**: `area_apt = float(area_arr[apt_mask].sum())`, stored into the per-scenario result dict at **L533**: `"area_km2": round(area_apt, 1)`. This is the exact same value, computed the exact same way (`build_pixel_area_array()` over the apt-pixel mask), that `_compute_integrated_area` in Phase 6 re-derives from scratch.
- **Why it's lost by the time Phase 6 needs it**: `potential_calculator.py::run()` strips `cap_map` and `zonal_df` from each scenario dict before returning (`_DROP_KEYS = frozenset({"cap_map", "zonal_df"})`, **L340**) but **keeps** `area_km2` — so in a same-process live run, `area_km2` is technically still present in the dict `results_writer.py` receives. **`results_writer.py` never reads it anyway** — `_compute_integrated_area` doesn't check `potential_results["techs"][tech]["scenarios"][scenario]["area_km2"]` first; it unconditionally re-opens the Phase 4 suitable-pixel TIF and recomputes.
- **The disk-recovery path makes this worse, not just redundant**: Phase 4's zonal CSV (`outputs/{ISO3}/potential/data/{CODE}_{tech}_{scenario}_zonal.csv`) has **no `area_km2` column** (only `capacity_mw_sum`, `generation_gwh` — confirmed by reading the write block at `potential_calculator.py:518-527`). So `src/utils/data_recovery.py::recover_potential_from_disk` (**L48-163**) cannot get area from the CSV either, and instead calls its own third implementation, `_extract_area_from_suitable_tif` (**`data_recovery.py:212-266`**) — which re-reads the same suitable-pixel TIF and re-runs `build_pixel_area_array()` a second time, independently of `results_writer._compute_integrated_area`. **Area is computed identically three separate times** (Phase 4 original, `data_recovery.py`'s recovery path, `results_writer.py`'s own path) with zero communication between the three.
- **Fix**: add `area_km2` (and ideally `capacity_gw`, `generation_twh` totals) as columns/rows to Phase 4's zonal CSV, or a small per-tech/scenario JSON sidecar written alongside it. Both `data_recovery._extract_area_from_suitable_tif` and `results_writer._compute_integrated_area` become unnecessary once that exists — read the number, don't recompute it.

### §2 — LCOE quartile statistics (p25 / median / p75)

- **Recalculated at**: `results_writer.py::_enrich_lcoe_stats`, **L294-354**.
- **Should be owned by**: **Phase 5** (`lcoe_calculator.py`).
- **Evidence Phase 5's stats are structurally incomplete in every path**:
  - Live-run dict: only `p10`, `p90`, `mean` are computed (per `_enrich_lcoe_stats`'s own docstring, confirmed — no `_compute_cf_and_lcoe`/stats-building code in `lcoe_calculator.py` was found writing `p25`/`median`/`p75`).
  - Disk-recovery: **even less** — `src/utils/data_recovery.py::_parse_lcoe_csv` (**L345-372**) extracts only a single **mean** value from the zonal CSV's `lcoe_mean` column; no percentiles at all survive this path.
  - Both paths therefore fall through to `_enrich_lcoe_stats`'s TIF-read branch (**L317-343**, re-opens `outputs/{ISO3}/lcoe/tif/{CODE}_{tech}_lcoe_usd_mwh.tif` and calls `np.percentile`) essentially every time — the "fallback" is, in practice, the normal path.
- **Fix**: `lcoe_calculator.py`'s stats-computation step (`_compute_cf_and_lcoe`, per `docs/arch-misalignments.md` §6) should compute the full percentile set once, from the same in-memory `lcoe_map` array it already has before writing the TIF, and persist all of them — in the zonal CSV (as additional columns) and/or a stats JSON. `_enrich_lcoe_stats` becomes unnecessary.

### §3 — Supply curve

- **Recalculated (approximated) at**: `results_writer.py::_recover_supply_curve_from_tif`, **L379-428** — using a **"1 MW per pixel" proxy assumption**, embedded as a bare `/ 1000.0` unit conversion at **L417**, with no named constant. The function's own docstring admits: "absolute GW totals differ from Phase 5."
- **Should be owned by**: **Phase 5** (`lcoe_calculator.py`).
- **Evidence Phase 5 computes the real curve but discards it**: `lcoe_calculator.py::run()`, **L891**: `supply_curve = compute_supply_curve(lcoe_map, cap_map)` — the real, pixel-accurate merit-order curve, using the actual per-pixel capacity map (not a 1 MW/pixel guess). This is stored at **L916** (`"supply_curve": supply_curve`) and used directly for `_plot_supply_curve` (**L1195-1200**) and for report thresholds (**L1498-1502**). Then, in the same `run()`'s final "Build serialisable result for the orchestrator" step (**L775-819**), the full `supply_curve` DataFrame is deliberately reduced to a **4-number summary** at **L808-815** (`n_points`, `min_lcoe`, `max_lcoe`, `max_capacity_gw`) — the real curve data points are discarded at this exact point and never written anywhere.
- **Confirmed there is no persisted file to recover from**: `grep -in "parquet\|supply_curve\.csv\|supply_curve\.to_" src/processors/lcoe_calculator.py` returns nothing. `src/utils/data_recovery.py::recover_supply_curve_from_disk` (**L440-**) is fully implemented to read `outputs/{ISO3}/lcoe/data/{CODE}_{tech}_supply_curve.parquet` (or `.csv` fallback) — **neither file is ever produced**, so this recovery function always returns `None` in practice, which is exactly the condition (`results_writer.py:372-374`, Tier 1 recovery returning `None`) that triggers the Tier-2 approximation.
- **Fix (matches `docs/arch-misalignments.md`'s recommendation)**: have `lcoe_calculator.py` write the real `supply_curve` DataFrame to Parquet (preferred, `recover_supply_curve_from_disk` already checks for it first) alongside the existing zonal CSV. `results_writer._recover_supply_curve_from_tif`'s approximation is then only ever a true last-resort (e.g., mid-migration before old runs get the new file), not the de-facto normal path it is today.

## Recommended moves, in priority order

1. **Persist Phase 5's real supply curve to Parquet** (`outputs/{ISO3}/lcoe/data/{CODE}_{tech}_supply_curve.parquet`, matching what `recover_supply_curve_from_disk` already expects). **Why first**: this is the only one of the three Phase 6 Overreach items with a *confirmed numerical divergence risk* already admitted in the code itself ("absolute GW totals differ from Phase 5") — every skip-mode/disk-recovered run of Phase 6 today is silently plotting and reporting an approximated curve, not the one Phase 5 actually computed. **What breaks if not done before the web platform**: any web UI surfacing per-technology supply/merit-order curves will show numbers that don't reconcile with Phase 5's own LCOE distribution stats for the same run whenever the two phases execute in separate processes/requests (which a request-driven web platform makes far more likely than the current single-process CLI pipeline) — a visible, explainable-to-a-reviewer inconsistency in a research tool.
2. **Add `area_km2` to Phase 4's zonal CSV** (or a small stats sidecar). **Why second**: three independent re-implementations of the same geodesic area calculation (`potential_calculator.py`, `data_recovery.py`, `results_writer.py`) is the highest-multiplicity duplication found across all three analysis passes — any future change to `build_pixel_area_array()`'s methodology has three call sites to keep in sync instead of one. **What breaks if not done**: low risk of numeric divergence today since all three genuinely call the same underlying function on the same TIF — but a future edit to any one of the three copies (e.g., a bug fix) will silently *not* apply to the other two, and a web platform re-triggering only "Phase 6 synthesis" for an already-computed country (a very natural web-UI action — "refresh the dashboard") will pay the TIF-re-read cost three separate times if it happens to also touch `data_recovery`'s path.
3. **Add full LCOE percentile stats (p25/median/p75) to Phase 5's stats output.** **Why third**: lower risk than #1 (no known numeric divergence — `_enrich_lcoe_stats`'s TIF-read fallback recomputes the *same* percentiles from the *same* TIF Phase 5 wrote, just redundantly) but still means Phase 6 cannot run its report step without re-opening a raster Phase 5 already fully read once. **What breaks if not done**: mainly a performance/architecture-cleanliness cost, not a correctness one — but combined with #1 and #2, it means Phase 6 currently re-reads *three different Phase 4/5 output rasters* to reconstruct data those phases already computed, which is the concrete substance behind `docs/arch-misalignments.md`'s "Phase 6 recalculates, it doesn't purely read + format" finding.
4. **Resolve the double-persistence in 5 phases** (§ I/O Abstraction Gaps) — decide once whether phase-level `ArtifactManager` calls or the orchestrator's automatic one is authoritative, and remove the other. **Why fourth**: doesn't produce wrong data (both writes are the same `result` object), but doubles disk I/O and pickle/JSON serialization cost on every phase of every run, and is exactly the kind of inconsistency ("some phases do X, some don't, no doc explains why") that makes onboarding a web platform harder — a new engineer wiring a web endpoint to "get Phase N's result" has to discover empirically which of two near-identical files is authoritative.
5. **Migrate Phase 4/5/6's raw `rasterio.open(..., "w")` calls to `safe_raster_write()`** (3 call sites). **Why fifth**: lowest risk — all three already set `compress="lzw"` themselves, so output *files* are similar; the main gain is eliminating the parent-directory-creation and guaranteed-close guarantees `safe_raster_write` provides for free, and normalizing `tiled`/`predictor` settings so GeoTIFFs produced by different phases are byte-for-byte comparable in structure. Do this last relative to #1-#4 since it's cosmetic/robustness cleanup, not a data-correctness or duplication-elimination fix.

No code was changed in this pass. As with the two prior analysis documents, no test suite exists (`docs/memory/06-risk-areas.md`) — any of the moves above should be verified by re-running the pipeline for an already-processed country and diffing `outputs/{ISO3}/` before/after, since #1-#3 in particular are expected to *change* what downstream phases compute, not just how the code is organized.
